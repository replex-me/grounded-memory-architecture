# 영속 코어의 변경 이력 교환과 복원

프로파일: `gma-journal/1`. 이 계약은 같은 `memory-store/1` 의미·토큰 계약을 구현한 저장소의 원자적 재생을 정의한다. 별도 구현과 상호운용을 실증했다는 뜻이 아니다. Python 0.1 참조 토큰 프로파일과 혼용하지 않는다.

## 포함하는 상태

원문과 출처, 기억의 모든 변경 요청, 관계·조건·검토, 구간 처리·사용 사건·요청 결과를 요청 순서대로 담는다. 원문을 현재 기억만으로 압축하지 않는다. 변경 요청을 정상 `apply` 계약으로 재생해 최종 상태를 검증한다. SQL 표를 직접 덮어쓰지 않는다.

검색·관계 색인은 재생 과정에서 파생한다. 적용 환경의 사용자·권한·기존 문서·원문 수집 포인터·호스트 설정은 포함하지 않는다. 따라서 이 형식은 코어의 교환 계약이며 조직의 전체 운영 DB 백업이나 권한 이관 계약이 아니다.

## 형식

- `format`: `gma-journal/1`.
- `profile`: `memory-store/1`.
- `requests`: 확정 순서의 `{hash, change, result}` 목록. 같은 요청 ID는 한 번만 나온다.
- `state_digest`: ID 순서의 현재 기록, 구간 처리, 사용 사건에 대한 코어 `digest` 값.
- `integrity`: 이 필드 자체를 제외한 교환 객체 전체의 `digest` 값.

변경 요청과 결과를 포함한 JSON은 코어의 정규화 계약으로 해시한다. 체크섬은 손상 검출이며 신뢰할 수 있는 발행자의 서명이 아니다. 발행자의 권한·의미 판단·출처 독립성은 해시가 입증하지 않는다.

## 내보내기와 가져오기

`exportArchive(store)`는 하나의 읽기 거래에서 이력과 상태를 읽고 원문의 해시를 확인한다. 원문·변경 이력을 포함하므로 공개 예제에는 합성 자료만 사용한다.

`importArchive(store, archive)`는 프로파일·형식·전체 체크섬·각 요청 해시·중복 ID를 확인한다. 대상의 기억 표는 비어 있어야 한다. 기존 기억과 조용히 병합하거나 채택 상태를 덮어쓰지 않는다. 모든 요청을 한 쓰기 거래에서 `apply`로 재생하고 각 결과 및 최종 상태 지문을 대조한다. 중간 요청 실패나 최종 상태 불일치이면 전체 재생을 취소한다.

같은 DB의 다른 표와 `user_version`을 바꾸지 않는다. 호스트의 기존 거래 안에서는 저장 지점을 사용하므로 호스트가 최종 확정을 맡는다. 적용 환경의 사전조건·후속 함수는 정상 변경과 마찬가지로 실행된다. 해당 환경의 외부 조건이 재생과 맞지 않으면 복원을 거부할 수 있다.

```js
import { MemoryStore } from '../runtime/store.mjs';
import { exportArchive, importArchive } from '../runtime/archive.mjs';

const archive = exportArchive(sourceStore);
const target = new MemoryStore(':memory:');
target.install();
try {
  const restored = importArchive(target, JSON.parse(JSON.stringify(archive)));
  console.log(restored);
} finally {
  target.close();
}
```

`sourceStore`는 적용 환경에서 열고 확인한 기존 코어 저장소다. 전체 실행 예제 `examples/persistent-demo.mjs`는 합성 원문과 여덟 단계 갱신을 만든 뒤 별도 빈 저장소에 복원해 현재 의미·검토·근거·이력의 동일성을 확인한다.

## 검증과 한계

공개 검사는 디스크 저장소의 재시작 후 왕복 동일성, 원문의 정확한 구간과 Unicode, 지지 집단·검토·구간·사용·요청 결과, 손상과 프로파일 오류, 중복 요청, 중간 실패와 최종 지문 불일치의 전체 롤백, 호스트 표 보존과 부모 거래 취소를 확인한다.

독립 구현과의 교환, 매우 큰 이력의 스트리밍, 여러 저장소의 충돌 병합, 원자료의 법적 삭제·보유 정책은 별도 계약과 평가가 필요하다. 현재 형식은 전체 이력을 메모리에 담으므로 큰 자료의 조회 경로로 사용하지 않는다. 정본 운영 데이터를 검증 없이 공개 교환 파일로 만들어서는 안 된다.
