# 공개 아키텍처 품질 재검토

검토일: 2026-10-14. 비교 기준은 공식 저장소·논문의 공개 기능과 규범 표준이다. 설치·운영·비교 실험을 모두 재현한 조사는 아니다. 다른 시스템에 어떤 기능이 없다고 단정하려면 해당 구현까지 확인해야 하며, 아래 표는 현재 확인한 강점과 우리에게 요구되는 수준을 구분한다.

## 비교해서 실제로 바뀐 판단

| 비교 대상 | 확인한 내용 | 이 설계에 대한 결론 |
| --- | --- | --- |
| Hindsight | 원자료를 근거로 관찰·믿음을 통합하고 계속 갱신되는 이해와 위키형 지식 페이지를 제공. 시작 예제·클라이언트·운영 문서·평가 경로도 있음 | ‘추출이 아닌 기억 관리’나 ‘살아 있는 위키’만으로 차별화할 수 없음. 전체 사용 흐름과 평가의 수준을 따라야 함 |
| A-MEM | 새 기록이 기존 기억의 속성·맥락·연결을 바꾸며 읽기·검색·수정 호출을 제공 | 동적 연결도 새로운 발명이 아님. 관계를 누가 왜 만들었고 무엇을 바꾸는지까지 명세해야 함 |
| HippoRAG 2 | 문서를 색인하고 연결을 통한 회상을 실행하는 예제와 연구 평가 제공 | 그래프를 갖췄다는 사실은 회상 품질의 증거가 아님. 실제 질의·데이터·비용을 고정한 비교 필요 |
| Eywa | 불변 원자료와 출처를 중심으로 장기 기억을 관리하는 가까운 선행 연구 | 원본 보존과 근거 연결 자체의 독점적 신규성 주장을 철회해야 함 |
| PROV·Web Annotation | 출처·변경 행위와 정확한 원문 구간을 명세 | 대응표만으로 표준 호환 구현을 제공했다고 주장할 수 없음 |

근거: [Hindsight 공식 저장소](https://github.com/vectorize-io/hindsight), [A-MEM 공식 저장소](https://github.com/agiresearch/A-mem), [HippoRAG 공식 저장소](https://github.com/OSU-NLP-Group/HippoRAG), [Eywa 논문](https://arxiv.org/abs/2605.30771), [PROV-O](https://www.w3.org/TR/prov-o/), [Web Annotation](https://www.w3.org/TR/annotation-model/).

Hindsight의 현재 공식 설명은 근거의 정확한 인용과 사건 수를 가진 관찰, 새 경험에 따른 기존 믿음의 정교화, 질문에 대한 지속적인 이해, 위키형 지식 페이지까지 포함한다. 과거의 네 기억 유형이나 단순 점수 갱신 설명만으로 현재 시스템을 비교하면 가까운 기능을 과소평가하게 된다. 이 재검토는 그 오류를 바로잡는다.

## 우리가 실제 제안하는 특징

이 아키텍처의 제안은 **위키의 현재 이해를 관리하는 명시적인 변경 계약**이다. 보존 원문과 의미 기억의 연결 경계, 역할별 관계, 조건별 독립 경험, 방향의 채택과 경험적 지지 분리, 읽은 버전에 묶인 정정, 의존 기억의 검토 만료를 하나의 작은 코어로 묶는다.

각 요소는 선행 연구·제품·표준에 이미 존재할 수 있다. 따라서 각각을 발명으로 소개하거나 다른 시스템이 모두 놓쳤다고 주장하지 않는다. 차이를 입증하려면 같은 경험을 넣었을 때 어떤 정정이 가능하고, 무엇을 잃지 않으며, 유지 비용이 어떻게 다른지 보여야 한다. 현재는 설계 선택과 실행 가능한 계약을 제공하는 단계다.

## 전문적인 공개 결과물의 기준과 현재 상태

| 기준 | 현재 제공 | 판정과 필요한 증거 |
| --- | --- | --- |
| 처음 보는 사람이 목적·작동·경계를 이해 | 새 소개와 아키텍처·관계·갱신 설명 | 문서 자체 검토 완료. 외부 독자의 이해도 미검증 |
| 비어 있지 않은 전체 시작 예제 | 여덟 단계 영속 예제, 구조화 출력과 설명 출력, 실제 결과 단언 | 로컬에서 재현 가능. 자동 의미 해석은 별개 |
| 구현과 독립된 의미·상태·변경 계약 | 코어 명세·기록 및 변경 스키마 | 초안. 전 규범의 검사 추적표와 외부 적합성은 미완성 |
| 실제 저장·동시 수정·실패·재시작 | SQLite 영속 코어와 실패·충돌 검사 | 합성 계약 검증. 다중 호스트 검증은 아님 |
| 갱신의 설명 가능성 | 당시 의미·원문·관계·이유·영향·요청 결과 | 실행 예제로 확인. 판단 이유의 의미 타당성은 사람이 확인 |
| 의미를 잃지 않는 이관 | 원문 버전과 구간 처리 목록의 계약 | 적용 환경의 의미 검토는 공개 합성 검증과 구별 |
| 신규 반례 발견 | 원문 검색과 관련 기억 읽기 경계 | 미연결 반례의 자동 발견·정확성 검증 미구현 |
| 독립 구현 교환 | Python·JavaScript의 같은 스냅샷 프로파일 검사·토큰 계산과 양방향 읽기 | 두 언어 간 스냅샷 검증 완료. 외부 독립 구현·영속 변경 이력의 언어 간 복원은 미검증 |
| 업무에서 더 좋은 결과 | 사전 고정 비교 평가 설계 | 실제 정확성·판단 시간·총비용 실험 미실행 |
| 권한과 삭제·복구 | 적용 환경의 책임·거래 경계 명시 | 공개 코어가 완성된 다중 사용자 권한 서버는 아님 |
| 공개 유지·확장·호환 | 라이선스·기여·보안·변경 기록 | 외부 검토·장기 지원 정책과 표준 안정화는 미완성 |

검사 수나 파일 수는 결과 품질의 대체 지표가 아니다. 최고 수준의 공개 레포라는 판단에는 실제 이해·사용 가능성, 정확한 구현, 재현 가능한 증거, 한계 공개, 외부 검토가 함께 필요하다.

## 이번 보완과 남은 핵심

이번에는 공개 주소와 명칭을 일치시키고, 핵심 소개를 목적→작동→최소 구조→실행→경계 순서로 다시 작성했다. 관계의 뜻과 강화·약화 때 바뀌는 내용을 설명했다. 합성 예제를 독립 성공·활용·반례·조건과 절차 정정·관계 재판별·별도 검토·재시작까지 확장했다. 특히 조건 문장만 고치고 관련 절차와 근거를 그대로 두었던 이전 예제의 불완전함을 수정했다.

가장 중요한 남은 일은 다음 순서다. 다양한 공개 합성 입력과 상반된 자료에서 판단 변화가 다음 사용까지 전달되는지 평가한다. 실제 조직의 자료·현황은 비공개 적용 환경에서 관리한다. 이후 같은 자료와 사전 고정 질의로 기존 문서 검색·원문 능동 검색·갱신 없는 그래프·갱신 있는 그래프를 비교한다. 두 언어 간 스냅샷 읽기 검증에 이어 외부 독립 구현과 교환하고 영속 변경 이력의 언어 간 복원도 확인해야 한다. 코어 검사 통과로 이 작업들이 완료됐다고 표시하지 않는다.

## 유지해야 할 단순함

더 많은 DB·에이전트·신뢰 점수·시각 효과를 추가하는 것이 이 부족함을 해결하지는 않는다. 원문 정본은 하나, 의미와 관계는 명시적, 변경은 원인과 읽은 버전에 묶고, 결과는 같은 거래에서 남긴다. 자동화는 이 경계 위에 변경안을 제안하는 방식으로 추가한다. 어떤 기능을 더할지는 실제 의미 손실·반례 누락·정정 실패·관리 비용의 증거로 결정한다.
